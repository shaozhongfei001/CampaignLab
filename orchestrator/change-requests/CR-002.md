# CR-002 · `listWorkspaces.status` 查询参数在契约内无对应字段

- 状态：OPEN（待契约负责人／项目负责人裁定）
- 提出时间：2026-11-12T23:44:54+08:00
- 提出人：编排器（依 M0-02/S1 设计 §7 Q4）
- 严重度：MINOR（有安全的过渡实现，不阻塞 M0-02）
- 影响面：`GET /api/v1/workspaces`（operationId `listWorkspaces`）、`Workspace` schema、`workspaces` 表

## 1. 事实（均磁盘实测）

- 活契约 `contracts/openapi.json` 中 `listWorkspaces` 声明了查询参数 `status`（长度 1–60）。
- `Workspace` schema 无 `status` 字段。
- `contracts/sqlite-v1.sql` 的 `workspaces` 表列为：
  `id, name, source_class, authorization_note, revision, created_at` —— **无 status**。
  （`status` 列存在于 `activities` 表，取值 `OPEN`/`ARCHIVED`，与 workspace 无关。）
- `architecture/API.md` 只写「按对应对象状态白名单过滤」，未给出 workspace 的状态白名单。

即：契约自身不一致——暴露了一个无法实现语义的过滤参数。

## 2. 为什么不由实现方补字段

补 `status` 字段等于**发明契约未规定的数据语义**，违反手册第 7 节「活契约是实现唯一依据」
与领域不变量「不得引入或伪造数据」；且 `workspaces` 表属 28 表参考 DDL，改它会破坏
「首迁与 sqlite-v1.sql 结构等价」这条 gate（表数 28、列与约束一致）。

## 3. 过渡实现（已裁定，M0-02 采用）

```
WORKSPACE_STATUS_WHITELIST: Final[frozenset[str]] = frozenset()
```

- 不传 `status` 或传空串：正常返回全部工作区分页。
- 传任何非空 `status`：返回 **422**，`code=INVALID_SCOPE`，
  `type=urn:campaignlab:problem:invalid_scope`（ADR-005），
  `issues[0].location="/query/status"`。
- 该行为可测、可取证，且不隐藏契约缺口（调用方会立刻看到 422 而非静默忽略参数）。
- 裁定后如需支持过滤，只改这一个常量即可（一行）。

## 4. 请求裁定的两个选项

| 选项 | 内容 | 代价 |
|---|---|---|
| A | 给 `Workspace` schema 与 `workspaces` 表补 `status`（如 `ACTIVE`/`ARCHIVED`），并给出白名单 | 改 28 表参考 DDL -> 破坏「首迁结构等价」gate，需同步改 spec 基线与 SHA256SUMS，属**基线变更**，代价高 |
| B | 从 `listWorkspaces` 移除 `status` 参数 | 只改活契约一处，不动 DDL 与 spec 基线；已实现侧只需删掉 422 分支，代价低 |

编排器建议 **B**。在裁定前，M0-02 按第 3 节过渡实现推进，不阻塞。
