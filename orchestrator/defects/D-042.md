## 1. 现象与实测

恒等式 `20 + 9 == 29` 在算术上成立，因此**任何只做加法核对的复核都会放过它**；但两个操作数**都与磁盘不符**（真值是 `26 + 3 == 29`）。即：恒等式为真、**代入值为假**——这是一类比「等式不平」更隐蔽的腐化形态，因为它能同时骗过人工目视与恒等式断言。

漂移量恰为 **6**，与 R11-T（提交 `4df3858`，lane T / Peirce / qwen3.8-flash）入库的 6 张 wave3 契约切片卡（M1-01、M1-02、M1-03、M2-01、M2-02、M2-03）**逐项对应**。该提交的 `counts_refresh_reason` 只记了「6 张 wave3 契约切片入库 + A170 终裁 + D-041/FU-33」，未见卡片三键的刷新记录；其后 R11-U1（`75ec2e1`）、R11-U2（`cf6dda1`）、R11-V（`cf39d64`）三次提交的 `counts_refresh_reason` 分别只刷新了 pytest/mypy 与 ruff 分母（482→490、78→79、222→225），**均未触及卡片三键**。故腐化自 `4df3858` 起持续 4 个提交、跨 2 个自然日。

## 2. 根因

**双重根因，缺一不会腐化这么久：**

① **写入侧**：A101 / `rule_counts_same_commit` 要求「counts 必须与新增文件在**同一次提交**内刷新」，但该规则的执行是**人工的**——由编排器在提交时逐项判断「本次新增了哪几类文件、该刷哪几个键」。R11-T 新增的是 `.md`（任务卡），编排器刷了 `ruff_formatted_files`（因为 `.md` 在 ruff 分母内）却**没有**把「任务卡」这一语义类别对应的 `task_cards_on_disk` / `known_missing_cards` 一并刷新。规则本身没错，错在**规则的落地面是「按文件后缀」而不是「按语义类别」**，导致同一批文件只触发了部分键的刷新。

② **守护侧**：`tests/unit/test_counts_freshness.py` 是 counts 新鲜度的**唯一**机器守护，而它的 docstring 与实现都只覆盖 `counts.ruff_formatted_files` 一个键（从 `git ls-tree -r HEAD` 重算 py+md 件数并与台账对账）。卡片三键**没有任何机器守护**。于是 ① 的错误在提交时未被拦下、在提交后也未被任何一轮全表门禁照到——490 个用例全绿，腐化静默存活。

**这不是 lane T 的过错**：lane 只交付卡片文件，台账写入权归编排器（`orchestrator/**` 在 lane 的 hard_deny 内）。

## 3. 责任归属

编排器（治理面：counts 刷新遗漏 + 守护覆盖缺口）。

## 4. 阻塞性判定

**不阻塞**：卡片三键不参与任何门禁的 rc 判定，`test_task_cards.py` 与 `test_task_card_narrative.py` 都从**磁盘与 `tasks` 键集**取数（而非从 counts 取数），故 26 张卡的派单与守护全部照常工作。

**但它有真实的下游危害**：手册 §15.5 与 A115 / `rule_no_hardcoded_symbol_counts` 规定「派单文**禁写死计数**、一律指向 `counts` 现值」。若 R12 的派单文照此规定引用 `counts.task_cards_on_disk`，就会把 **20** 这个假现值写进 lane X 的上下文，而 lane X 的任务恰是补齐卡片——一个偏小 6 的现值会让 lane 对「还缺几张」产生错误预期，进而可能撞上「实测 != 台账」的**假 RED**（这正是 `test_counts_freshness.py` docstring 里描述的同一类事故形态）。故必须在 wave3 派单前校正。
