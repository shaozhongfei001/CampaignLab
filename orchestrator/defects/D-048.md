# D-048 · 设计文档缺陷：`M2-01-design.md` §11.3 的**一般规则**（所有写 UPDATE 的 WHERE 必须含 guard 镜像）与 §3.2 给出的 `set_current_rule` **SQL 原文**（谓词只有 `workspace_id` + `id`）互相矛盾 —— 实现方照哪一条都会违反另一条

- **owner**：编排器

## 1. 事实（实测，非转述）

| 出处 | 原文（逐字摘录） | 对 `set_current_rule` 的要求 |
|---|---|---|
| §11.3 的 `infra/db/repositories.py` 段 | 「所有写 UPDATE 的 WHERE 谓词必须含 §3 的 `guard` 镜像（`status='OPEN' AND revision=:revision` / `state='DRAFT' AND revision=:revision` / `state='DRAFT' AND revision=:revision AND digest=:digest`）」 | 谓词**必须**含 `status`/`state` ＋ `revision` 镜像 |
| §3.2 的「`activities.current_rule_id` 的联动（冻结）」段 | `UPDATE activities SET current_rule_id=:rule_id, revision=revision+1 WHERE workspace_id=:ws AND id=:activity_id` | 谓词**只有** `workspace_id` ＋ `id` |

同一段 §3.2 还明文「物理保证＝UPDATE 谓词带 `state='DRAFT'` ⇒ `rowcount=0`（**禁先 SELECT 后 UPDATE 的裸检查**）」，
即：想给 `activities` 那条 UPDATE 补 `revision` 镜像，就必须先读活动行拿到它的当前 `revision`，而这被同节禁止。
⇒ 两条规范**在物理上不可同时满足**，不是措辞松紧问题。

## 2. 根因

§11.3 是 S2b-1 的**写权面清单**，为省事把「所有 UPDATE 都要带 guard 镜像」写成了一条无例外的通则；
§3.2 是**状态机章**，给的是逐条 SQL 原文。两处由不同轮次写入、彼此没有交叉引用，
通则没有为「联动型 UPDATE（改的是**另一张表**的派生列，其 guard 由本事务内前一条 UPDATE 承担）」留出例外。

## 3. 影响

- lane 无论照哪一条都会违反另一条 ⇒ 只能上报 U 项、等编排器裁定（本棒用了 loop 2-of-3 里的一部分做归因）。
- 若不裁定就入库，后续 S3/S4（`api/activities.py`、`api/rules.py`）与 M2-03（`receipts`）会**各自猜测**口径，
  产生「同一条 SQL 在不同棒里谓词不同」的分叉实现 —— 这是静默分叉，不会报错，比判红更危险。
- 交付面本身无缺陷：lane 按 A214 逐字实现了 §3.2 的 SQL 原文，并在 docstring 里写明了理由（可追溯）。

## 4. 处置（本批同批落地，A224）

**A232 裁定：维持 §3.2 的 SQL 原文（specific 覆盖 general），零代码改动。** 三条理由与残留风险逐条写在
`M2-01-design.md` §14.2（本批以 A214 窄豁免文末追加，前 1322 行逐字节未变）。要点：

1. A214 要求逐字实现 design 给出的 SQL 原文；具体规范优先于一般通则。
2. 补 guard 在物理上需要一次额外 SELECT，而 §3.2 明文禁止裸先查后改。
3. 并发安全已由**同一事务内**规则侧的 `state='DRAFT' AND revision=:revision AND digest=:digest` 谓词承担，
   且 `revision=revision+1` 是相对自增（不丢更新）。

**残留风险（如实登记）**：`current_rule_id=:rule_id` 是绝对赋值 ⇒ 「同一活动的两个规则版本被并发确认」时
后到者覆盖先到者，理论上可能使 `current_rule_id` != §3.2 定义的「`confirmed_at` 最大者」。
SQLite 单写者 ＋ 事务串行化下窗口极窄 ⇒ 归 **FU-54**（M2-01/S6 必须把该行为钉成用例；
若真实并发下判红，再立缺陷走 CR，可能要把谓词改成 `WHERE ... AND (current_rule_id IS NULL OR revision=:revision)` 形态）。

## 5. 防再发

设计文档里写「所有 X 必须 Y」这类**无例外通则**时，必须同批做两件事：
① 用脚本把文档里出现的**全部 SQL 原文**抽出来，逐条检查其 WHERE 是否满足该通则，不满足的**当场列成例外清单**写进同一节；
② 通则里显式写「例外见 §N」，禁留「读者自行判断」。
本条与 PRE-15（派单文读数由脚本实测）同源：**凡是「所有／一律／必须」的量化断言，都要有脚本把分母跑一遍**，
否则它就是下一个 lane 的假红来源。机器化归 FU-53 的派单文／设计文生成器需求面。
