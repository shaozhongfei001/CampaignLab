## 1. 失真原文（design §11.5，绝对行 1087–1089，逐字）

```text
私有 `_rule_check_response(check, *, request_id)`
（把 `BoundaryCaseDraft.input_payload` 交给 `CaseInput` 做 `model_validate`，**校验失败即 500 `INTERNAL_ERROR`**：
框架自己生成的反例不合法属服务端缺陷，禁静默丢弃）
```

## 2. 实测事实（三处失真，逐个给命令与输出）

| # | 原文声称 | 仓内实测 | 命令 |
|---|---|---|---|
| ① | 存在符号 `BoundaryCaseDraft` | **不存在**。实名为 **`BoundaryCase`**（在 `api/common.py.__all__` 的 79 项内实取） | `getattr(common,'BoundaryCaseDraft')` → `AttributeError`；`'BoundaryCase' in common.__all__` → `True` |
| ② | 该 Model 有字段 `input_payload` | **无此字段**。实测 4 字段＝`id` / `label` / **`input`** / `verification`，`extra='forbid'` | `list(BoundaryCase.model_fields)` |
| ③ | `CaseInput` 可 `model_validate` | **不可**。`CaseInput` 不是 Model 而是 `Annotated` 别名：`Annotated[CouponCaseInput \| CallbackCaseInput, FieldInfo(discriminator='template')]` ⇒ 实测 `hasattr(CaseInput,'model_validate') is **False**`，照原文写会 `AttributeError` | `type(CaseInput).__name__` → `_AnnotatedAlias`；`hasattr(...)` → `False` |

**关键的第三层含义（比字面失真更重要）**：`BoundaryCase.input` 的注解**实测就是**
`CouponCaseInput | CallbackCaseInput`（判别联合，`discriminator='template'`）⇒ pydantic 在 **service 侧构造
`RuleCheck` 时**就已完成校验。非法反例在**类型上不可达**响应层 ⇒ 原文要求的
「校验失败即 **500 `INTERNAL_ERROR`**」分支是**结构性不可达**的。

## 3. 影响

- **对 S4（`api/rules.py`）**：若照失真原文实现，会得到一个**运行期即崩**（`AttributeError`）或
  **永远走不到**的 500 分支；且为了「覆盖」它而写的用例必然**必红**（或被迫 `skip`/`xfail`，
  违反 design §6.6 的禁 skip 口径）。
- **对 S6（`tests/api/activities/**`）与 S7（`evidence/M2/**`）**：若下游按失真原文写断言，
  会产出必红用例与无法取证的判据 ⇒ **必须**在它们的派单文里同步 A256 口径。
- **对 AC-004**（条款确认门禁 / 检查项框架）：**无影响** —— 该 AC 的判据面在
  `checkRule` 的 `issues` 与 `boundary_cases` 内容上，不依赖「响应层二次校验」这一实现细节。

## 4. 处置（A256）

**裁定 A256**：`_rule_check_response(check, *, request_id)` **只做透传组装**，
**不做二次校验、不设 500 `INTERNAL_ERROR` 分支**。design 的原意（「框架自己生成的反例不合法属
服务端缺陷，禁静默丢弃」）由**上游构造期校验**满足 —— `BoundaryCase.input` 是已校验的判别联合，
非法数据无法被构造出来 ⇒ **强度不降**（校验点从「响应层事后补救」前移到「构造期即时拒绝」，
这是**更强**而非更弱的位置）。

**连带义务**（禁悬空）：

1. design §11.5 原文按 **D-011 不改写**；本单与 A256 是它的**权威读法**。
2. **S4 派单文已逐字携带 A256**（§5），并要求 lane 在回执 §9 显式声明
   「§11.5 的 500 分支依 A256 不实现，理由＝上游已校验」。
3. **S6 / S7 派单时必须同样携带 A256 ＋ 本单编号**，禁让下游按失真原文写必红用例。
4. 本单在 S4 入库批时随 `s4_delivered_R18` 一并登记 `related_defects`，禁只在设计文侧留痕。

## 9. R18-11 更正附录（编排器在 M2-01/S4 入库批复核时发现；上文原文**一字不改**，D-011）

**本单的 ①② 两条断言事实错误，③ 正确；A256 的裁定结论不变，但其「理由」必须按本节重述。**

### 9.1 复核触发点

S4 lane（昵称 Wegener）回传后，编排器按 PRE-29 **独立复验**（禁采信自报）。复验时对
`BoundaryCaseDraft` / `input_payload` 做了**全仓**实存对撞（本单原先只在 `api/common.py` 一个模块内找）：

```bash
uv run --no-sync python -c "
import importlib, dataclasses
dom = importlib.import_module('campaignlab.domain.activity')
print('BoundaryCaseDraft' in dom.__all__)
print([f.name for f in dataclasses.fields(dom.BoundaryCaseDraft)])
"
```

### 9.2 实测事实（与本单原文对撞）

| 本单原断言 | 实测 | 判定 |
|---|---|---|
| ① 仓内**无** `BoundaryCaseDraft`，实名 `BoundaryCase` | `campaignlab.domain.activity.__all__`（55 项）**含** `BoundaryCaseDraft`；定义在 `src/campaignlab/domain/activity/checks.py:171`，是 `@dataclass`，字段实测 `['id','label','template','input_payload','verification']` | **错** |
| ② 该 Model **无** `input_payload` 字段，实名 `input` | 领域侧 `BoundaryCaseDraft` **有** `input_payload: Mapping[str, Any]`；`input` 是**API DTO 侧** `api/common.py:667 class BoundaryCase` 的字段名（实测 `['id','label','input','verification']`）。两者是**同一事实的领域形与契约形**，不是「设想名 vs 实名」 | **错** |
| ③ `CaseInput` 不是 Model 而是 `Annotated` 别名，`hasattr(CaseInput,'model_validate')` 为 False | 复测一致：`type(api.common.CaseInput).__name__ == '_AnnotatedAlias'`、`hasattr(...,'model_validate') == False` | **对** |

### 9.3 根因（本单自己的根因分析漏了一层）

本单 §root_cause 说的是「设计文未对具名符号做仓内实存对撞」。**编排器在立本单时犯了同一个错**：
对撞范围只取了 `api/common.py`（因为 design §11.5 的上下文是响应层 DTO），**未扩到领域层**
`domain/activity/checks.py` ⇒ 把「DTO 侧没有」误当成「仓内没有」。这是 **PRE-24 / PRE-25 的
范围性失误**（符号实存对撞必须**全仓**，禁限定在单个模块），已由 **R18-11** 登记、
并由 **PRE-33** 补齐防再发。

### 9.4 A256 的结论为何**不变**（理由重述）

design §11.5 要求 `_rule_check_response` 把 `BoundaryCaseDraft.input_payload` 交给 `CaseInput`
做 `model_validate`、失败即 500 `INTERNAL_ERROR`。实测真实链路：

1. `deps.RuleService.check_rule(...) -> RuleCheck`（**返回的已是 API DTO**，不是领域 Draft）；
2. `application/activity_service.py:1925` 实测就是转换点：
   `BoundaryCase.model_validate({"id":…, "label":…, "input": draft.input_payload, "verification":…})`；
3. 故 Draft→DTO 的**校验发生在应用层**，路由层拿到的 `RuleCheck.boundary_cases` 已是
   `list[BoundaryCase]`，其 `input` 已被判别联合校验过。

⇒ 路由层**确实无事可校验**，A256 的处置（`_rule_check_response` 只透传、不设 500 分支）
**结论正确**。但本单 §fact 的「**更深一层**：非法反例在**类型上**不可达响应层」这一表述
**不准确**：`input_payload` 的静态类型是**未校验的** `Mapping[str, Any]`，非法载荷在类型上
**是可达**转换点的；真正使 500 分支在路由层不可达的原因是**校验点位于应用层**（位置更靠前＝更强），
而非「类型上不可达」。强度判定（校验点前移＝不降强度）**不变**。

### 9.5 连带影响

  前半句**准确**（正是 §9.4 的第 2 点），后半句沿用了本单的失真表述。
  **处置**：交付件**一字不改**（保留 lane face `389L/17913B/c7b3cccee6ec` 的可审计性），
  本附录即其权威读法；S6 / S7 派单文**必须**携带本附录，禁再抄 §fact 的「类型上不可达」。
