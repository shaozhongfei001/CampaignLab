## 1. 现象（实测，逐条可复现）

| # | 权威来源 | 实测内容 |

| 1 | `orchestrator/handoff/M0-02-design.md:26` | `async def exchange_session(payload: SessionExchange, request: Request, svc: SessionService = Depends(get_session_service)) -> Response`，并声明 413 `INPUT_TOO_LARGE` |
| 2 | `orchestrator/handoff/M0-02-design.md:30` | `async def create_workspace(payload: WorkspaceCreate, idempotency_key: str = Header(...), actor: Session = Depends(require_session), svc: ...) -> Response`，并声明 413 `INPUT_TOO_LARGE` |
| 3 | 同文件 §4/§7.3 | 413 必须经 `common.read_body_within_limit(request, max_bytes=...)` 的**两阶段**判定（先量长度、再解析） |

即：§1 冻结的 DTO 形参与 §4/§7.3 的正文限流口径**不能同时成立**。

## 2. 技术根因（为什么互斥）

FastAPI 对 pydantic DTO 形参会在**进入路由体之前**自行读取并消费请求体流。路由体内再调
`read_body_within_limit` → `request.stream()` / `await request.body()` 时，流已被消费：
轻则拿到空字节（长度判定恒 <= max_bytes，413 永不触发），重则抛 `RuntimeError`（Stream consumed）。
结果是契约声明的 **413 变成不可达分支**，`INPUT_TOO_LARGE` 与 AC-034 的「上传失败 -> 413」取证面同时丢失；
而 413 是 `PROBLEM_STATUSES` 与切片状态码集合的成员，静默不可达比显式报错更难被发现。

## 3. 裁定（A94，本轮生效）

两个 POST 路由的**正文形参改取 `request: Request`**，在路由体内经
`common.read_body_within_limit(request, max_bytes=...)` 手工读取、再由
`parse_json_body[ModelT]` 完成 JSON 解析与 DTO 校验（400 正文非 JSON/Content-Type 错、422 字段级、413 超长各归其位）。
**其余形参名、`Depends` 注入位、`-> Response` 返回类型逐字不变**；`createWorkspace` 的
`Idempotency-Key`（`Header(alias=...)`）与 `actor: Session = Depends(require_session)` 保持冻结原样。

design §1 的冻结签名按「历史值只加注不改写」纪律处理：**原文字节保留**，本缺陷单即其注记；
design 文件本身不在本提交写集内（S3b 写集为 4 文件，见 §4）。
