## 2. 缺陷定性

v1.0.1 补丁**自身内部不一致**：`architecture/MONTHLY-REVIEW.md` 以反引号书写、形态上是 Problem `code` 字面量的两个值，
既没有被 `contracts/monthly-contract-delta.json` 加进活契约，也没有被加进 ADR-005 §2.1 冻结的 20 码注册表。
若 M3-P01/M4-P01 照 spec 字面实现，`domain/errors.py` 必须扩到 22 码 → 触碰公共冻结件与 `check_contracts.py` 登记项分母，属 CR 级变更；
若照注册表实现，则与 spec 原文不符，`AC-MR-04`「范围冲突 422」的 code 断言无法逐字取证。二者必居其一，**不能由执行 lane 自行选择**。

## 3. 处置选项（请项目负责人裁定；编排器推荐 A）

- **选项 A（推荐，零契约变更）**：把 `MONTHLY_INVALID_SCOPE` / `MONTHLY_REPORT_KIND_REQUIRED` 认定为 spec 的**语义标签**而非 code 字面量，实现分别复用已在 20 码内的 `INVALID_SCOPE`（422，范围冲突）与 `VALIDATION_ERROR`（422，kind 非法），
  在 `Problem.detail` 与 `Issue.code`（自由串 1–96，非冻结面）里承载 `MONTHLY_INVALID_SCOPE` / `MONTHLY_REPORT_KIND_REQUIRED` 字样以保留可追溯性。
  代价：`AC-MR-04`/`AC-MR-09` 取证时 code 断言写作 `INVALID_SCOPE` 并在证据里注明标签映射；不动契约、不动注册表、不重切 11 份切片。
- **选项 B（契约变更，成本高）**：走 CR 把两码加进 `contracts/openapi.json` 的 Problem code 枚举与 ADR-005 注册表（20→22），
  随后必须：重跑 `check_contracts.py`、按 D-020 的 `--depth 5` 重切全部 11 份切片（指纹全变）、更新 `M0-02/S3a` 已交付的 `PROBLEM_CODES` 与 110 个用例中涉及 20 码分母的断言、并在 `API.md` 权威表登记。
  与 CR-002（选项 B 移除 `listWorkspaces.status`）不同，本次是**新增**冻结面，回滚成本更高。
