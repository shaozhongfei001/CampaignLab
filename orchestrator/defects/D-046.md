# D-046 · 工装缺陷：`scripts/orch_harness.py::frozen_tree()` 导出的「冻结索引树」**并未与活动工作树隔离** —— `.venv` 里的 editable 安装 `.pth` 硬编码了活动仓库的绝对 `src` 路径，故冻结树上跑 pytest/mypy 时 `import campaignlab` 全部解析到**活动工作树**，门禁读数可能是「冻结测试 ＋ 活动源码」的杂交结果

- **发现方**：编排器（R15 入库 M0-04/S2c 时冻结树门禁判红，逐条定位后发现红因不可能由暂存集产生）
- **发现时点**：2026-11-15T00:40:00+08:00
- **严重度**：MAJOR　**blocking**：false（有可靠规避手段，见 §6①）　**status**：OPEN
- **归属任务**：GOVERNANCE（工装面；与 FU-39 同域）
- **owner**：编排器
- **权威证据**：编排器 2026-11-15 于 `/home/szf/dev/CampaignLab` 实测：
  - `cat .venv/lib/python3.14/site-packages/_editable_impl_campaignlab.pth` → 单行 **`/home/szf/dev/CampaignLab/src`**（绝对路径，指向**活动**工作树）
  - `scripts/orch_harness.py:199-213` 的 `frozen_tree()`：`git checkout-index -a -f --prefix=<scratch>/` 后，
    对 `(".venv", ".git")` 两个名字执行 `dst.symlink_to(src)` ⇒ 冻结树里的 `.venv` **就是**活动仓库的 `.venv`
  - 触发实例：暂存集只含 lane Y2（M0-04/S2c）的 9 个文件、**不含** `api/common.py` 与 `tests/unit/test_domain_errors.py`，
    而冻结树门禁报 `FAILED tests/unit/test_domain_errors.py::test_common_public_surface_is_unchanged`。
    该用例在**活动工作树**上单跑为 **pass**（`api/common.__all__` 实测 78、断言 78）；
    在冻结树里它是 HEAD 版（断言 51），却 `import` 到活动树的 `api/common.py`（78 项）⇒ 必然红。

## 1. 现象与实测

冻结树的设计意图（`run_commit` docstring 第 4 步、R11-3、A101）是：**索引此刻 == 待提交树**，
在从索引导出的树上跑四门，从而保证「门禁照到的正是即将入库的内容」。

实测该保证**对 Python 导入不成立**。`sys.path` 里由 editable `.pth` 注入的是
`/home/szf/dev/CampaignLab/src` 这个**绝对路径**，与 `cwd` 无关；`frozen_tree()` 又把 `.venv` 软链进 scratch，
所以 `<scratch>` 里跑 `pytest` 时：

| 面向 | 实际取自 | 是否冻结 |
|---|---|---|
| 测试文件本身（`tests/**`） | `<scratch>/tests`（pytest 按 rootdir 收集） | ✅ 冻结 |
| `import campaignlab.*` 解析到的源码 | **`/home/szf/dev/CampaignLab/src`（活动树）** | ❌ **未冻结** |
| `mypy` 的 `files = ["src","tests","scripts"]` | `<scratch>/…`（相对 cwd） | ✅ 冻结（但 follow-import 仍可能落到活动树） |
| 靠 `Path(__file__).parents[n]` 定位的守护（如 `test_clock.py` 的 `SRC`） | `<scratch>/src` | ✅ 冻结 |

于是门禁读数是**杂交**的：测试逻辑是冻结的，被测源码可能是活动的。

## 2. 触发条件与既往影响面

**触发条件（三者同时成立才会显形）**：
① 有 lane 在飞且**修改了已被跟踪的 in-scope 文件**；② 该修改**未**进入本次暂存集；
③ 冻结树里有测试会 `import` 到那个模块。

既往各轮之所以**没有**暴露：历次「一 lane 入库、另一 lane 在飞」的场景里，在飞 lane 的产物都是
**新增未跟踪文件**（如 `evidence/**`、新建 `.py`），而不是对已跟踪文件的修改 ——
未跟踪文件不在索引里，也就不在冻结树里，而冻结树里的测试又不会去 import 它们，故相安无事。

本轮是**首次**出现在飞 lane（M2-01/S2a）修改了两个已跟踪文件（`api/common.py` +401/−0、
`tests/unit/test_domain_errors.py`）而编排器先入库另一条 lane（M0-04/S2c）的情形，条件①②③首次同时成立。

⇒ 结论：**既往入库的门禁读数不受影响**（不满足触发条件），但「冻结树」这一保证的**强度一直被高估**，
台账里 `run_commit` docstring 与 R11-3 / A101 的措辞（「索引此刻 == 待提交树」）在导入面上并不成立。

## 3. 根因

`frozen_tree()` 为了让工具链能原地跑而软链 `.venv`，但**没有同时中和 editable 安装的绝对路径**。
软链 `.venv` 是必要的（否则要重装依赖，代价不可接受），漏的是「让冻结树的 `src` 在导入解析上优先于
`.pth` 里的绝对路径」这一步（例如给 pytest/mypy 注入 `PYTHONPATH=<scratch>/src`，或在 scratch 内放一个
优先级更高的 `.pth`/`conftest` 钩子）。

## 4. 阻塞性判定

**不阻塞**，但**必须显式规避**：若不规避，门禁会产生两种方向的错误 ——
**假红**（本轮实例：暂存集无过错却判红，白耗一次 100 s 全表跑）与更危险的
**假绿**（冻结树里本该红的代码，因 import 到活动树上「已被后续 lane 修好」的版本而变绿 ⇒ 让不合格的内容入库）。
假绿形态尚未在本仓出现过，但它逻辑上完全可能，故定级 **MAJOR**。

## 5. 修复范围

① 编排器的入库流程（立即可用的规避手段 ＋ 机器可判的前置断言）；
② `scripts/orch_harness.py::frozen_tree()` / `run_gates()`（根治，归 FU-39 的工装批次）；
③ 一条防回归的机器守护（断言冻结树确实隔离）。

## 6. 修复方案

**①（本轮立即采用，已生效）——「入库前工作树必须与暂存集一致」**：
在调用 `run_commit` 之前，编排器必须先**停泊（park）**所有不属于本次暂存集的在飞改动
（未跟踪件移到仓库外暂存目录并记 sha256 清单；已跟踪件的修改先备份再 `git checkout --` 还原到 HEAD），
入库完成后再逐件**按 sha256 校验还原**。如此活动树 == 索引 == 冻结树，杂交面消失。
该动作作为 **PRE-12** 记入 `resume.dispatch_preconditions_note_R15`，并由入库脚本在 `run_commit` 前
**程序化断言**：`git diff --name-only`（未暂存的已跟踪改动）必须为空，否则 `SystemExit` 拒绝入库。

**②（FU-39 工装批次，根治）**：`run_gates()` 对 pytest 与 mypy 注入 `PYTHONPATH=<tree>/src`（并把 `<tree>` 置于最前），
使冻结树的 `src` 在导入解析上优先于 editable `.pth` 的绝对路径；实施时必须先验证
`sys.path` 的实际优先级（`uv run --no-sync` 可能重解析环境），**验证通过前不得移除 ①**。

**③（FU-39 同批，防回归）**：新增守护，在临时目录里造一个「冻结树与活动树对同一模块给出不同常量」的场景，
断言冻结树上跑出来的读数是**冻结树的值**而非活动树的值；该守护必须自带正向对照（故意不隔离时能判红）。

**④（文档面）**：`run_commit` 的 docstring 与 R11-3 / A101 的措辞按 D-011 **不改写**，
改为在本单与 `resume.gate_measurement_caliber` 里追加「冻结树的隔离性在 Python 导入面上不成立，
须以 PRE-12 规避」的更正注记。
