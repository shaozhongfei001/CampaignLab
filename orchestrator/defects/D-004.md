# D-004 契约切片工具的数据源钉死在 v1.0.0 基线，spec_version 硬编码，会向月报任务静默提供过期契约

- 严重级：**MAJOR**（静默失效；尚未污染已交付物，但会让 5 个月报任务拿到 1.0.0 的契约上下文）
- 发现者：Lane T（编排器），2026-11-12「开工充分条件」核查中，执行手册 13.3 第 3 条差分回归时发现
- 受影响对象：`scripts/contract_slice.py` —— 全体子智能体上下文包的唯一生成器，属公共工具

## 现象（实测，非推断）

| 位置 | 实测内容 |
|---|---|
| 第 22 行 | `SPEC = Path("spec/CampaignLab-SDD-v1.0")` |
| 第 64 行 | `api = load(SPEC / "contracts/openapi.json")` |
| 第 106 行 | `pages = cast(list[Json], load(SPEC / "contracts/pages.json"))` |
| 第 117 / 133 行 | `(SPEC / "contracts/sqlite-v1.sql").read_text(...)` |
| 第 149 行 | `bundle: Json = {"spec_version": "1.0.0"}` —— 版本号**硬编码**，不从任何契约读取 |

即：切片工具的 openapi / pages / DDL **全部**只从不可变基线读取，从不读活契约 `contracts/`。
而活契约 `contracts/openapi.json` 的 `info.version` 已是 **1.0.1**（CR-001 / ADR-004 / CHANGES.json 12 节点）。

复现：用 D-001 修复后的工具按 wave1 原入参重切，`spec_version` 仍输出 `1.0.0`：
```
$ python3 scripts/contract_slice.py --ops exchangeSession,getSession,getHealth,listWorkspaces,createWorkspace \
    --ac AC-001,AC-034,AC-035 --out /tmp/M0-02.new.json      rc=0
old M0-02 spec_version: 1.0.0    new M0-02 spec_version: 1.0.0
M0-02: 除 spec_version 外内容字节等价 = True
M0-03: 除 spec_version 外内容字节等价 = True
```

## 定性：这是「合入 v1.0.1 之后才成为缺陷」

工具写于 02:40，当时活契约是基线的**逐字节副本**（见 `contracts/PROVENANCE.md`），两者等价，钉基线无害。
20:24 合入 v1.0.1 后活契约与基线**开始分叉**，而工具未随之改源 —— 于是「实现唯一依据是活契约」
（手册第 7 节、PROVENANCE 第 3 条）在上下文包这一层被悄悄绕过。

**流程缺口（比脚本本身更值得修）**：手册第 7 节第 4 条要求契约变更集同步
「OpenAPI + operations.json/pages.json + 受影响 ui 说明 + 测试 + fixture 期望」，
**没有把「读基线当活契约用的工具」列入同步清单**。M0-P01 因此漏改本工具，且没有任何门禁能发现。

## 影响面（据实分级，不夸大）

1. **wave1（M0-02 / M0-03）内容不受影响**，已实测证明：
   - v1.0.1 的 12 个节点只触及 `Review`、`ReviewCreate`、7 个 `Monthly*` schema、source-json/source-metadata；
   - 实测 schema 差集：`live - base` 恰为 `MonthlyCapacity/Comparison/OriginOverlap/Participation/Production/Review/Trend`，
     `base - live` 为空；
   - wave1 的 5 个 operationId（exchangeSession、getSession、getHealth、listWorkspaces、createWorkspace）与之无交集；
   - 重切后除 `spec_version` 外**字节等价**（上表）。
   → 结论：wave1 切片内容正确，**仅版本戳是假的**，不需要重做内容，只需重切以修正版本戳与来源标记。
2. **wave4/5/7/8/9 会被静默污染**：M1-P01、M3-P01、M3-P02、M4-P01、M5-P01 都要用月报 schema。
   按现状切片会缺 7 个 `Monthly*` 与 `Review.monthly_review`、`ReviewCreate.profile`、
   `source-metadata.monthly_review`，子智能体将按 1.0.0 实现，直到 M0-03 那条
   「openapi-typescript 产物 diff 为空」门禁才暴露；返工会落在 slack=4 / 2 / **0** 的任务上，
   其中 M4-P01、M5-P01 无浮动可吸收。
3. `spec_version` 字段本身是假值：任何依赖它做版本判断的下游逻辑都会得到错误结论（属「工具恒旧且不报错」）。

## 修复方案（属 wave1 派单前置，尚未执行）

1. 数据源改活契约：`contracts/openapi.json`、`contracts/pages.json`、`contracts/sqlite-v1.sql`
   （活契约目录已含全套 12 个文件；`sqlite-v1.sql` 与基线逐字节相同且受门禁强制不漂移，故改源不改内容）。
2. `spec_version` 从活契约 `info.version` 读取，**禁止硬编码**；输出中追加
   `source_openapi`（路径）与 `source_sha16`（该文件 SHA256 前 16 位），使上下文包可追溯来源字节。
3. 保留 `--base` 类开关以便对基线切片（用于差分回归），但**默认必须是活契约**；
   若显式指定基线，`spec_version` 输出为 `1.0.0-baseline` 以免与活契约混淆。
4. 差分回归（13.3 第 3 条）：对 wave1 原入参重切，除 `spec_version`/`source_*` 外必须与已入库切片字节等价。
5. 篡改负例 + 分母断言（15.4）：`--ops` 中任一 operationId 在活契约缺失 → rc=2，禁静默；
   新增用例：把活契约某 op 改名后重切必须非 0。
6. `tests/unit/` 增用例钉住：切片源＝活契约、`spec_version` == `info.version`、未知 op rc=2、
   `source_sha16` 与 `contracts/openapi.json` 实算一致。
7. 重新生成并入库 `orchestrator/handoff/M0-02.slice.json`、`M0-03.slice.json`（`spec_version` 应为 1.0.1）。
8. 同一变更集内更新 `contracts/PROVENANCE.md`（登记工具改源）与手册第 7 节第 4 条同步清单
   （补入「读基线当活契约的工具」），并在本单写复测记录。
