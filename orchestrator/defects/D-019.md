# D-019 · ADR-005 未指向 Problem.code 的权威枚举表，429 一度被判为「契约缺项」

- 严重度：**MINOR**（文档指向缺失；未造成错误实现，但导致一次误判与一轮无谓核查）
- 状态：FIXED_PENDING_Q
- 发现时间：2026-11-13T04:05:00+08:00（D-016 补卡批次 1 的 D14 项，编排器复核后重新定性）
- 发现者：Dirac（T lane，qwen3.8-flash，D14 上报）+ 编排器复核
- 证据：`docs/decisions/ADR-005-problem-type-and-runtime-defaults.md` §2.1、
  `spec/CampaignLab-SDD-v1.0/architecture/API.md` 错误分类表（第 20–29 行）、`orchestrator/tasks/*.md` 中的 code 引用

## 1. 事实

`ADR-005` §2.1 规定了 `Problem.type` 的 URN 方案
（`urn:campaignlab:problem:` + `code.lower()`），并声明
「`code` 注册表由 `src/campaignlab/domain/errors.py` 单一来源定义」，
但**没有指出 code 的取值集合来自哪份权威文档**。

实际上权威枚举就在 spec 内：`spec/CampaignLab-SDD-v1.0/architecture/API.md` 的「错误分类」表（第 20–29 行）已按 HTTP 状态
完整列出 code，编排器逐行提取实测 **20 个**：
BAD_REQUEST、BAD_CURSOR、SESSION_EXPIRED、ORIGIN_DENIED、ACCESS_DENIED、RESOURCE_NOT_FOUND、
IDEMPOTENCY_CONFLICT、STATE_CONFLICT、VERSION_MISMATCH、STALE_CANDIDATE、SNAPSHOT_CONFLICT、
ACTION_REVIEW_REQUIRED、REVISION_CONFLICT、PRECONDITION_REQUIRED、INPUT_TOO_LARGE、
VALIDATION_ERROR、INVALID_SCOPE、EVIDENCE_REQUIRED、**JOB_CAPACITY（429）**、INTERNAL_ERROR。

后果实例：补卡过程中 429 一度被判为「契约缺项、需新立裁定」（Dirac 的 D14 初判），
经编排器复核 `API.md` 后确认**早有权威定义**，真缺陷只是 ADR-005 未指向该表。

## 2. 影响

- 实现方（S/F/D lane）在写 `errors.py` 与各 API 的错误分支时，若只读 ADR-005，
  会以为 code 集合需要自行设计，从而**各自发明**，破坏 ADR-005 §2.1 的「单一来源」意图。
- 429 `JOB_CAPACITY` 属 M0-04（jobs 容量）与 M5-01（性能）的判定依据，
  漏掉会让「作业排队超限」退化成 500 `INTERNAL_ERROR`，AC 判定失真。
- Q 档复核时无权威表可比对，只能判「实现自述一致」，失去独立性。

## 3. 修复方案（本次提交）

1. `ADR-005` §2.1 增补**权威指向**：code 取值集合以 `spec/CampaignLab-SDD-v1.0/architecture/API.md`
   错误分类表（第 20–29 行）为唯一权威枚举，`domain/errors.py` 是该表的**代码化副本**，
   不得新增表外 code；如需新增，先改 ADR（走 CR）再改注册表。
2. 明确 **429 → `JOB_CAPACITY`** 已在权威表内，不属契约缺项，无需另立裁定。
3. 补卡时凡引用 code，一律逐字取自该表（Dirac 已按此执行：20 个 code 名逐字命中
   `API.md:22-29`），并在卡内标注出处行号。

## 4. 教训

ADR 规定「方案」时必须同时给出「取值集合的权威出处」，否则单一来源只是形式。
判定「契约缺项」前必须穷尽 spec 内的 architecture/*.md（手册第 0 节裁定优先级第 2 项
包含「包内领域契约」，不只是 `contracts/openapi.json`）。
