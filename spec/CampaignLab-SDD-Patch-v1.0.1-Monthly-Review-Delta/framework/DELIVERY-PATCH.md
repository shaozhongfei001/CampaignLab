# 开发计划增量 · 月报先形成可验业务闭环

## 交付次序

- M0 开发已启动时，用同一工作区接续。M0 的工具链、环境、会话、作业与原迁移仍是基础。M2 的赠券和回拨可沿原依赖并行。
- M1 发布能力可用后先打通月报最小输入切片。数据、分析、前端在受控契约确定后可并行：分析以固定样本测试，前端以真实类型和固定响应做组件开发，再汇合到实际 API。
- M3 同阶段先出「全行月报 → 企微缺采和共同范围 → 参与度及重复触达证据」；随后合入渠道容量、客群及产能细分。M4 接上报告版本与行动。优先安排该闭环作为新增验收样例。
- M5 原赠券与回拨两条路径继续全量回归。月报形成第三条走查，单列结果。实际银行口径验证使用授权后续任务处理，合成设计实现、验证和启动无须等现场取数。

## 回执与边界

各任务回执记录版本、提交、环境、命令与退出码、输入快照或文件摘要、问题与可查证路径。建议证据路径 `evidence/monthly/<任务号>/<运行号>/`。对真正的缺数输出工作区、周期、影响及取数责任；合成样例由开发和 QA 直接完成。凡涉及行内真实分母、口径归属、客户键或容量定义的修改，按原 AGENTS 的业务裁定流程登记。

可交付的月报必须从文件导入跑到报告、签认、补采更正和下期观察，在浏览器能打开相关证据。仅执行补丁校验只证明包结构、差异和合成算术。应用自测、独立 QA、项目负责人验收各自登记。
